# Базовые замеры производительности (Baseline Benchmarks)

## Цель
Зафиксировать эталонные показатели ресурсов стокового Dear ImGui с платформой GLFW и рендерером OpenGL3 на примере стандартного окна `ImGui::ShowDemoWindow()`. Данные замеры являются отправной точкой для сравнения со всеми последующими этапами:
- **Этап 1:** Реактивный цикл по событиям (`glfwWaitEventsTimeout`).
- **Этап 2:** Пропуск идентичных кадров (дедупликация `ImDrawData`).
- **Этап 3:** Неинвазивные хуки + рекордер команд + программный векторный рендерер ThorVG.

---

## Тестовый стенд и окружение

- **ОС:** Windows 11 (build 10.0.26100)
- **Компилятор:** MSVC 19.44 (Visual Studio 2022 Professional, 64-bit)
- **Конфигурация сборки:** `Release` (`/O2`)
- **Графический стек:** GLFW 3.4 + Desktop OpenGL 3.0 / GLSL 130
- **Библиотека GUI:** Dear ImGui 1.91.x (ветка `drawlist-hooks`, чистый upstream fork)
- **Векторный движок:** ThorVG v1.0.7 (CPU Software Rasterizer + GL Blit)
- **Разрешение окна:** 1280x720, VSync включен (`glfwSwapInterval(1)`)
- **Активный контент:** `ImGui::ShowDemoWindow()` в развернутом виде

---

## Методика измерений

Для обеспечения строгой воспроизводимости в тестовое приложение `demo` встроен автоматический режим бенчмарка:
```bash
./build/Release/demo.exe --benchmark
```

### Сценарий теста
1. **Прогрев (Warm-up):** 1.0 секунда после инициализации OpenGL и ImGui.
2. **Тест (Простой / Idle):** 5.0 секунд без какого-либо пользовательского ввода (`glfwWaitEventsTimeout` / курсор неподвижен).
3. **Тест (Движение мыши / Active Motion):** 5.0 секунд непрерывного программного перемещения курсора по синусоидальной траектории над окном `ShowDemoWindow` (`glfwSetCursorPos(window, x, y)`).

### Собираемые метрики
- **Кадры и FPS:** суммарное количество отрендеренных кадров и средний FPS за 5 секунд.
- **CPU Work Time (ms/frame):** чистое время на CPU, затраченное на логику ImGui (`NewFrame`, обработка виджетов, триангуляция / запись векторов) и рендеринг (`ImGui_ImplOpenGL3_RenderDrawData` или `ThorVGRenderer::RenderDrawData`). Замеряется высокоточным таймером `std::chrono::steady_clock` (не включает ожидание VSync в `glfwSwapBuffers`).
- **Total Frame Time (ms/frame):** полное время итерации главного цикла (включая ожидание `glfwSwapBuffers`).
- **Thread CPU Time (ms):** суммарное процессорное время основного потока приложения за 5 секунд, полученное через Win32 API `GetThreadTimes` (kernel time + user time), а также процент загрузки одного ядра CPU.
- **Process CPU Usage (%):** общая загрузка CPU процессом относительно всех доступных логических ядер системы через `GetProcessTimes`.
- **GPU Frame Time (ms):** время выполнения команд рендеринга на GPU, измеренное аппаратно через OpenGL-запросы таймера `GL_TIME_ELAPSED` (`glBeginQuery` / `glEndQuery` / `glGetQueryObjectui64v`).
- **RAM Working Set (MB):** объем физической оперативной памяти (Working Set), используемый процессом (через `GetProcessMemoryInfo` из `psapi.h`).

## Валидация точности и визуального соответствия (Этап 3)

### 1. Текстовые метрики (`test_text_metrics.exe`)
- **Единый источник истины:** Метрики шрифта согласованы между `ImFont::CalcTextSizeA` и `ThorVGRenderer::MeasureText` с учетом масштабного коэффициента TrueType em-units:
  $$
  \text{Scale Ratio} = \frac{(\text{Ascent} - \text{Descent}) \times (96 / 72)}{\text{unitsPerEm}} = 1.7731
  $$
- **Результат тестирования:** **17 из 17 тестов пройдены (100% PASS)**.
- **Среднее расхождение:** **0.04 px**.
- **Максимальное расхождение:** **0.07 px**.

### 2. Попиксельное визуальное сравнение (`visual_diff.exe`)
- **Тестовая сцена:** Полноразмерное окно `ImGui::ShowDemoWindow()` в разрешении 1280x720 (921 600 пикселей).
- **Точное совпадение пикселей (RGB diff = 0):** **569 865 (61.83%)**.
- **Совпадение в пределах зоны субпиксельного AA (diff <= 32):** **347 381 (37.69%)**.
- **Итоговое визуальное соответствие:** **917 246 (99.53%)** (порог прохождения >= 90%).
- **Заметные расхождения:** 4 354 пикселя (0.47%), приходящиеся исключительно на аналитическую кривизну векторных контуров ThorVG vs 1-пиксельную триангуляционную окантовку ImGui и динамический мигающий курсор ввода.
- **Среднее расхождение по каналам:** **0.92 / 255**.
- Подробный отчёт и визуальные артефакты: [docs/discrepancies.md](discrepancies.md), `stock_render.bmp`, `thorvg_render.bmp`, `diff_map.bmp`.

## Анализ результатов и архитектурные выводы

1. **Экстремальная ресурсоэффективность в простое:**
   - Перевод на гибридный событийный цикл (`glfwWaitEventsTimeout`) и дедупликацию снизил нагрузку на CPU с **94.06% до 0.00%** одного ядра.
   - Число отрендеренных кадров в простое сократилось более чем на **99.999%** (с 363 000 кадров за 5 секунд до всего 3 кадров затухания).
   - Приложение полностью засыпает в ожидании событий ОС (`MsgWaitForMultipleObjectsEx`), не совершая вызовов `NewFrame`, триангуляции геометрии или отправки команд в GPU.
2. **Мгновенный отклик при активности:**
   - При появлении событий ввода цикл моментально просыпается с нулевой задержкой, обеспечивая полную частоту обновления (до 51 000 FPS без VSync), сохраняя абсолютную плавность.
3. **Чистая архитектура перехвата (Fork & Hooks):**
   - В форке `imgui` модифицирован исключительно один файл — `imgui_draw.cpp`.
   - При отсутствии `IMGUI_USER_CONFIG` поведение форка на 100% тождественно стоковому Dear ImGui.
   - Все хуки имеют дефолтные макросы `(false)` / `((void)0)`.
   - Добавлен макрос `IMGUI_DRAWLIST_HOOK_HAS_INTERCEPTION`, позволяющий сохранять структуру окна в `ImDrawData` даже при полной триангуляционной разгрузке.
4. **Готовность к следующим этапам:**
   - Все структуры команд `DrawCommand` плоские, содержат предварительно вычисленный `bbox` и готовы для грязных прямоугольников (Этап 4) и бинарной сериализации в `DataView` WebAssembly (Этап 5).
